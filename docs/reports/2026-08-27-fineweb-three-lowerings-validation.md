# FineWeb 链接清理、语言过滤与版权清理：完整流水线性能验证报告

## 阅读约定：A–G 配置与比较口径

本报告比较 FineWeb 完整文本处理流水线在关闭 UDF 优化、开启既有优化，以及叠加三个新增表达式下沉优化时的耗时和输出一致性。测试于 2026-08-26 至 2026-08-27 完成，以下数据整理自已有实测，没有重新运行基准。

### A–G 分别是什么

所有配置均运行同一提交 `python-udf-jit@dcd3836`，业务步骤、输入和公共运行环境保持一致，通过开关区分执行路径。三个新增优化编号固定为：**第 1 项＝链接清理（U01），第 2 项＝语言过滤（M01），第 3 项＝版权清理（U03）**；不是流水线步骤编号。

**既有优化**包括 HTML 清理、标点转换、空白规范化、长度过滤的原生表达式路径，以及字母数字比例过滤的 typed JIT 路径。开启 `UDFJIT_MODE=auto`、`UDFJIT_COLUMNAR=1` 表示允许使用这些已有能力，不意味着所有 UDF 都会编译。

| **A** | 关闭 UDF 优化；总收益参照 | off | 0 | 0 | 0 | 0 |
| **B** | 仅开启既有优化；新增优化的增量基线 | auto | 1 | 0 | 0 | 0 |
| **C** | B ＋第 1 项 | auto | 1 | 1 | 0 | 0 |
| **D** | B ＋第 2 项 | auto | 1 | 0 | 1 | 0 |
| **E** | B ＋第 3 项 | auto | 1 | 0 | 0 | 1 |

### 如何读后面的结果

- **总收益 A/X**：A 的平均耗时除以 X 的平均耗时，包含既有优化和新增项的整体效果。
- **增量收益 B/X**：同一比较块中 B 的平均耗时除以 X 的平均耗时，用于衡量新增下沉；X 为 C、D、E、F 或 G。
- **基础收益 A/B**：单独衡量既有优化，不能归功于三个新增项。
- **模型模式**：stand-in 使用替代算子；real-KenLM 将困惑度过滤换成 SentencePiece＋KenLM。两者的语言过滤均为字符集正则启发式，不是 fastText；输入均为冻结 FineWeb 数据。

`A/B` 等斜线表示耗时比，不是分支名。`B3` 等数字后缀表示运行轮次。ABBA 表示“对照→候选→候选→对照”的四次执行顺序，每种配置两轮。

A/B 及 B/C、B/D、B/E、B/F、B/G 有同块 ABBA 证据；总收益 A/C、A/D、A/E、A/F、A/G 是不同块实测均值的比值，标为**跨块观察**，不作为直接配对结果。G 只在当前归档的 200K 数据中有结果，20K 留空。后文均沿用这些定义。

## 1. 测试对象：完整 FineWeb 文本处理流水线

Python UDF 是逐条处理文本的 Python 函数；Daft 负责构造和执行列式数据处理计划，Ray 负责分布式执行。本次“表达式下沉”指 UDF JIT 识别受支持的函数语义后，在 Daft 执行计划中使用原生字符串或比较表达式，减少目标计算经过 Python UDF 调用的开销；没有为本实验重写业务流水线，也没有新增 CinderX 后端优化。

测试使用冻结的 FineWeb 文本 Lance 数据集，分别为 20,000 和 200,000 行。流水线包含下列 13 个业务步骤，最后写入 Lance；每种配置的步骤和顺序相同。表内“保留已有优化”描述 B–G；A 关闭 UDF JIT 接入，但仍执行全部业务步骤。

| 顺序 | 处理步骤 | 本次相关配置或变化 |
|---:|---|---|
| 1 | HTML 清理 | 保留已有原生正则表达式优化 |
| 2 | 链接清理 | 本次优化点：删除匹配的 URL |
| 3 | 邮箱清理 | 不变 |
| 4 | 版权清理 | 本次优化点：删除匹配的版权声明 |
| 5 | Unicode 修复 | 不变 |

### 两种模型模式分别代表什么

两种模式使用相同的冻结文本输入和上述业务链；“stand-in”描述算子实现，不表示使用了合成输入。

| 模式 | 环境开关 | 困惑度过滤 | 语言过滤 | 结果的适用含义 |
|---|---|---|---|---|
| stand-in（替代实现） | `VOLC_REAL_TEXT_OPS=0` | 采用测试框架的替代实现 | 六语言字符集正则计数启发式 | 替代算子完整链下的收益 |

### 如何比较以及为什么基线耗时不是一个固定值

每个模式和规模分别执行四个独立 ABBA 块：`B3→C1→C2→B4`、`B5→D1→D2→B6`、`B7→E1→E2→B8`、`B9→F1→F2→B10`。每个优化配置只与本块的两个基线样本比较，不跨块共用基线。因此，同一规模的结果表中会出现多个略有差异的基线均值：它们来自各自独立重跑的基线，不是采用了不同的基础优化配置。

统计采用每种配置两个样本的算术均值：

- 加速比 = 基线平均耗时 / 优化后平均耗时。
- 耗时下降 = `(1 - 优化后平均耗时 / 基线平均耗时) × 100%`。
- 两个配对加速比分别用第一轮基线 / 第一轮优化后、第二轮基线 / 第二轮优化后计算。

例如 stand-in 200K 的三项组合是 `294.442682 / 157.008019 = 1.875335×`，耗时降低 `46.68%`；不能把 `1.875335×` 写成“耗时降低 87.53%”。

另有四个基础优化块，各模式/规模按 `A1→B1→B2→A2` 执行；第 1＋3 项组合在两种模式的 200K 下分别按 `B11→G1→G2→B12` 执行，没有复用其他块的 B。

总计包含原有 16 个单项/三项组合块、4 个基础优化块和 2 个链接＋版权组合块，即 22 个独立比较块、88 次计时。新增优化的增量比较为其中 18 个块，另 4 个块衡量基础优化收益。计时指标是完整运行的 `metrics.elapsed_s`，不是目标算子的局部耗时；包含 Ray 初始化及末端物化、所有业务算子和 Lance 写入。

## 7. 结论边界与证据追溯

配套 JSON 是本报告的仓库内证据入口：`comparisons` 保存 88 轮计时及 22 个同块比较，`overall_comparisons` 保存 22 个总收益比值并指向同文件内的比较 ID。所有均值、加速比和耗时下降均可直接根据内嵌样本重算；总收益派生值不增加测试轮数。

`comparisons[].correctness.embedded_sink_comparison` 保存 10 份内容比较摘录，可核对行数、schema 及输出摘要。其他正确性结果、Windows 测试及 epoch 状态保留证据级别，不能视为仓库内可重新执行的完整验证。

JSON 中的 `source_snapshot` / `source_snapshots` 仅保存已检查来源的字节 SHA256 和大小，不含文件名或路径。这些是来源身份元数据，不是文件引用；没有原始字节就不能重新核验这些来源哈希。模型名称和指纹同样只是受测环境元数据，不表示模型文件随仓库提供。

- 每臂仅两轮计时，不提供置信区间，也不把本轮正收益当作跨机器、跨数据集的稳定性保证。
- M01 只针对当前精确 helper 和参数；real-KenLM 模式也不代表 official fastText。
- Links 和 Copyright 只针对已限定的正则签名与 replacement。
- 缺少显式 epoch 的运行环境不在本次验证范围内；本分支没有混入 epoch 源码修复。
- 本仓库证据不包含原始运行文件、模型、输入数据集及完整 Lance 输出；可重算计时收益，但不能仅凭报告与摘要重跑整个实验或重新比较全部输出。

本文仅链接配套 JSON 和本仓库实现/测试文件。JSON 的文件引用集中于 `repository_files`，路径统一相对仓库根目录；比较 ID 是同一 JSON 内部引用。
